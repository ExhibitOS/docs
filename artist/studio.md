# Studio 로컬 초안, 공간 편집과 복원

Studio 개발판의 `/studio`는 계정 없이 전시 문서의 로컬 초안을 만들고,
방·벽·바닥·천장·문·창문과 표면 재질을 편집하며 제한된 3D 미리보기로 확인하는
화면이다. 같은 문서를 JSON으로 편집·자동 저장하고 이력과 파일 백업으로 복원한다.
작품 배치 편집기, 작품 Viewer와 publication은 후속 기능이다.
실행 명령과 검사 환경은 [Platform README](https://github.com/ExhibitOS/platform#readme),
API와 저장 형식은 [Studio 안내](https://github.com/ExhibitOS/platform/blob/main/docs/studio.md),
공간·재질 계약은 [공간 편집 안내](https://github.com/ExhibitOS/platform/blob/main/docs/studio-geometry.md)를 따른다.

## 오프라인 작업 준비

먼저 연결된 상태에서 production 웹의 `/studio`를 열고 오프라인 앱 준비가
완료됐는지 확인한다. 이 과정은 공개 앱 코드를 저장한다. 이후 같은 브라우저
프로필과 origin에서 연결을 끊고 `/studio`를 다시 열 수 있다. 최초 설치를
오프라인에서 할 수는 없으며 Vite development 서버는 이 보장을 제공하지 않는다.

‘새 로컬 전시’를 누르면 계정이나 서버 요청 없이 draft를 만든다. 제목과 전시
문서 JSON을 편집하면 유효한 문서만 자동 저장된다. 공간 치수, 표면·개구부,
작품 배치·transform, navigation·accessibility와 작품 snapshot을 문서에 보존한다.
단위는 meter, 좌표계는 right-handed Y-up이며 현재 규격은 `1.0.0-draft.1`이다.
잘못된 구조·참조·단위·quaternion 등은 거부하고 마지막 완료된 저장본을 유지한다.
작품 파일 bytes는 이 단계에서 가져오거나 검증하지 않는다. 편집 입력은 UTF-8
1,000,000 bytes, 서버 전체 요청은 wrapper 포함 1 MiB 한도다. 공개 규격의
문서 한도에 가까운 JSON도 입력·요청 한도 때문에 거부될 수 있다.

## 공간 편집과 적용

로컬 초안을 새로 만들거나 다시 열고 ‘공간 · 표면 · 개구부 편집’에서 요소를
선택한다. ‘방 추가’로 방을 만들고 이름·치수·위치·회전을 입력한 뒤 ‘선택 요소
속성 적용’을 누른다. 입력 필드만 바꾸면 문서에 적용되지 않는다. 명령은 전체
문서 유효성을 검사한 뒤 같은 로컬 자동 저장과 선택적 서버 저장 경로를 사용한다.
잘못된 치수·회전·참조는 적용하지 않으며 이전 문서와 undo 이력을 유지한다.

표면이 없는 방에서 ‘선택 방 white-cube 생성’을 누르면 벽 4개, 바닥과 천장을
만든다. 기존 표면을 덮어쓰지 않는다. 방 치수를 나중에 바꿔도 기존 표면의 치수와
위치는 자동으로 바뀌지 않으므로 각 표면을 명시적으로 수정한다.

치수와 위치는 meter다. 방의 transform은 전시 좌표 기준이고 표면의 transform은
소유 방 기준이다. 표면은 중심이 원점인 두께 없는 XY 직사각형이며 회전 전 법선은
+Z다. 회전은 정규화된 XYZW quaternion이고 방·표면 scale은 `[1,1,1]`로 고정한다.
크기는 scale 대신 치수로 편집한다. 회전이 없는 transform의 예는 위치
`[0,0,0]`, 회전 `[0,0,0,1]`, scale `[1,1,1]`이다.

벽을 선택하고 ‘선택 벽에 외부 문 추가’로 사각 개구부를 만든 뒤 문·창문 종류,
폭·높이와 벽 중심 기준 XY 위치를 적용한다. 전체 개구부가 벽 안에 있어야 한다.
바닥에 닿는 문의 Y 중심은 `(문 높이 − 벽 높이) / 2`다. 예를 들어 높이 4m 벽에
높이 2m 문을 만들면 Y 중심은 −1m다.

문은 외부 출입문이거나 서로 다른 방의 문과 연결된 쌍이다. 문을 선택하고 다른
방의 문을 골라 ‘두 문 연결’을 누르면 양쪽 참조를 함께 적용한다. 연결 해제도
양쪽에 함께 적용하며 외부 문으로 바꾼다. 연결된 문은 먼저 해제한 뒤 삭제한다.
문 연결은 서로의 참조를 검증하며 실제 공간의 인접 여부나 보행 가능성을 보장하지
않는다. 다른 요소가 참조하는 방·표면·개구부는 참조를 먼저 수정하거나 제거해야
삭제할 수 있다. 참조 없는 표면을 삭제하면 해당 재질 지정도 같은 명령에서 삭제한다.
기존 작품·권리·navigation과 다른 확장 metadata는 유지한다.

‘공간 편집 undo’와 ‘공간 편집 redo’는 현재 편집 세션의 최근 20개 명령을 다룬다.
undo 후 새 명령을 적용하면 redo가 비워진다. 화면을 다시 열거나 JSON 교체,
로컬 복원, 명시적 서버 적용으로 문서가 바뀌면 새 명령 이력을 시작한다.
저장된 로컬 초안 이력은 별도로 유지되므로 아래 이력 복원 절차를 사용한다.

## 표면 재질과 호환성

표면을 선택해 색상·거칠기·금속성을 입력하고 ‘표면 재질 적용’을 누른다.
‘표면 재질 기본값’은 해당 지정을 제거한다. 기본값은 색상 `#f4f1e8`, 거칠기
`0.8`, 금속성 `0`이다. 텍스처나 외부 URL은 불러오지 않는다.

공개 기본 OES에는 표면 PBR 필드가 없으므로 문서의 extensions에 선택적 Platform
확장 `org.exhibitos.studio/materials` version 1로 저장한다. 기본 OES 규격 버전은
바뀌지 않는다. 기존 문서에 이 확장이 없어도 기본값으로 편집할 수 있으며 다른
OES 클라이언트는 이 확장을 무시할 수 있다. 기존 초안의 migration은 필요 없다.

이 확장의 최상위 필드는 `version`과 `surfaces`뿐이다. 각 surface UUID의 지정은
`color`, `roughness`, `metalness` 세 필드로 구성한다. 색상은 소문자 6자리 hex이고
거칠기·금속성은 0–1의 유한한 숫자다. 최대 64개 지정, 직렬화된 확장 데이터
16 KiB로 제한한다. 실제 표면 참조와 UUID 대소문자 중복을 검사하고 알 수 없는
확장 버전은 거부하며 원문을 다시 쓰지 않는다. 브라우저 저장과 인증된 서버
POST/PUT에서 같은 검사를 수행하고 다른 확장 namespace는 보존한다.
정확한 구조는 [공개 재질 schema](https://github.com/ExhibitOS/platform/blob/main/contracts/studio-materials.schema.json)를 확인한다.

## 3D 미리보기와 한도

로컬 미리보기는 방·표면 transform, 실제 사각 벽 cutout과 PBR 재질을 표시한다.
‘선택 표면 정면’은 표면의 바깥쪽에서 개구부를 확인한다. ‘전체 공간 보기’,
‘위에서 보기’, ‘시점 왼쪽 회전’, ‘시점 오른쪽 회전’ 버튼은 키보드로도 포커스를
이동해 실행할 수 있다. 시점 변화는 단계별이며 연속 애니메이션을 실행하지 않는다.

검증된 미리보기 범위는 방 32개, 표면 256개, 개구부 128개, 생성 사각 패널
8192개, 좌표·치수 10,000m 이내다. 한도를 넘는 유효한 문서는 보존하고 JSON으로
편집할 수 있지만 미리보기 불가 메시지를 표시한다. WebGL을 사용할 수 없어도
숫자 편집과 JSON 백업을 사용할 수 있다. 재질의 시각적 결과는 조명과 브라우저에
따라 달라진다.

이 화면은 공간 형상 확인용이다. 작품 파일 bytes를 불러오거나 검증하지 않고,
작품 배치 편집·전체 Viewer·전시 공개를 제공하지 않는다. 곡선벽·계단·벽 두께·충돌
물리·imported mesh 방이나 조명 시뮬레이션도 지원하지 않는다.

## 저장 실패와 이력 복원

다른 탭이 먼저 저장하면 현재 입력과 최신 저장본을 비교하고 새 사본을 만든다.
충돌한 입력으로 최신 기록을 자동 덮어쓰지 않는다. 이전 이력의 복구는 새로운
version을 추가하며 기존 이력을 유지한다. 화면에는 최신 50개 이력을 표시하며 더 오래된
이력도 저장소에 남고 원문 구조 백업에 포함된다. 사본은 새 draft·exhibition·revision ID를
사용하고 서버 계정 연결을 제거한다.

Quota 부족, 중단된 저장, 손상된 기록이나 새 버전 기록의 오류를 보면 현재 입력을
파일로 백업한다. 저장본·현재 입력 백업은 정상 저장본 JSON과 미저장 입력 text를
별도로 다운로드한다. 브라우저 저장 공간을 정리하기 전에 실제 다운로드 파일을
확인한다. 브라우저 데이터 삭제·eviction·기기 장애는 이력까지 없앨 수 있다.
이 구현은 draft나 이력, 이전 앱 캐시를 자동 삭제하지 않는다.

형식 1의 정상 기록은 형식 2로 이동하며 원문을 남긴다. 다른 탭이 업그레이드를
막으면 해당 탭을 닫고 ‘저장소 다시 읽기’로 재시도한다. 손상·미래 형식은 덮어쓰지
않는다. ‘원문 구조 백업’은 진단용 raw JSON이며 정상 백업 import 파일과 다르다.

정상 JSON 백업을 복원하면 유효성을 검사한 뒤 새로운 독립 사본을 만든다.
기존 기록을 대체하지 않는다. 백업은 문서 metadata이며 작품 파일, 자격정보나
전체 OEX 패키지를 포함하지 않는다. 작품 파일은 별도로 백업해야 한다.

## 선택적 서버 저장

[Artist CMS](cms.md)에서 로그인한 뒤 Studio에서 현재 서버 계정을 명시적으로
확인한다. 로그인이나 온라인 전환만으로 초안을 서버에 전송하지 않는다.
Artist·curator는 자신의 초안을 관리하며 admin은 같은 기관의 초안을 관리한다.
다른 소유자·기관·viewer에게 private authoring 접근을 허용하지 않는다.

서버 저장은 강한 ETag와 현재 계정·기관 권한을 확인한다. 다른 편집으로 서버가
바뀌면 412 충돌을 표시하고 입력을 보존한다. 서버 내용을 비교한 뒤 명시적으로
로컬에 적용하거나 현재 입력을 비교한 서버에 적용하거나 별도 사본을 만든다.
비교 후 서버가 다시 바뀌면 새 적용도 거부한다.

응답이 유실된 요청의 정확한 재시도는 기존 revision을 반환한다. 이 값이 최신
서버 상태라는 뜻은 아니므로 이후 적용 전에 현재 서버 내용을 비교한다.
재시도 intent는 현재 화면 memory에 있다. 다시 연 뒤에는 서버 내용을 읽어
비교하고 명시적으로 이어간다. 연결된 draft와 현재 계정이 다르면 동기화를 막는다.

로컬 초안은 브라우저 프로필·origin 단위이며 로그아웃 후에도 남는다. 공유
브라우저에서 계정별로 격리된 비밀 저장소가 아니다. private 로컬 작업은 별도
브라우저 또는 OS 프로필을 사용한다. Offline worker는 API·인증·draft 응답을
캐시하지 않으며 서버는 매 요청의 현재 권한을 검사한다.

새 앱 버전은 명시적인 적용 또는 이전 탭이 닫힌 뒤 활성화된다. 적용 전에
파일 백업을 보관한다. 앱 코드의 캐시 성공과 초안의 장기 보존은 별개다.
